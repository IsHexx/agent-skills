# 缺陷草稿生成规范（Agent 用）

提缺陷分**两种场景**，先判断属于哪种，再按对应规范执行。判断规则：

- 用户明确说「用户反馈/客服反馈/原样提交/批量导入」→ **场景B**
- 用户发来测试中发现的「截图 + 描述」提缺陷（默认）→ **场景A**
- 拿不准时问用户一句，不要猜

---

## 场景A：日常项目迭代提缺陷（严格模板）

按以下【分析要求】和【缺陷报告模板】生成，目标是描述准确、可直接开发定位。

### 分析要求

1. **对比需求**：若用户在对话中提供过需求文档，结合需求识别功能实现与业务逻辑的偏差；没有需求文档时不得编造需求依据。
2. **UI推断**：准确推断截图中的页面位置（菜单路径）、涉及控件的含义及当前异常状态。
3. **精准步骤**：复现步骤必须包含具体的输入数据和页面动作，杜绝「随便」「任意」「某些」等模糊词汇；截图里没有的数据不要编造，看不清的数值在确认环节向用户核实。
4. **输出限制**：草稿直接输出 Markdown 代码块，不要任何前后引导语或原因猜测（原因猜测属于开发排查范畴，不写进缺陷单）。

### 缺陷报告模板

````markdown
【缺陷标题】
【模块名称/路径】
简述问题现象（例如：【设置-辅助设置-客户】备注字段校验与UI提示不一致导致保存异常）

【复现步骤】
1. [第一步：进入路径/页面位置]；
2. [第二步：具体操作+输入数据]；
3. [第三步：触发动作并观察结果]。

【实际结果】
1. [描述截图标注区域的具体异常表现]；
2. [描述系统弹窗、数据状态等不符合预期的点]。

【预期结果】
1. [基于业务逻辑说明正确的表现]；
2. [UI 提示应与后端校验逻辑保持一致，形成对照]。
````

### 提交方式

确认后将内容组织为 bug JSON 调 `scripts/create_bug.py`：

- `title` = 缺陷标题（即模板首行「【模块-子模块】对象+现象」简述）
- `module` = 模块名称/路径
- `steps` = 复现步骤数组（不带编号，脚本统一编号）
- `actual` = 实际结果（多条用换行连接）
- `expected` = 预期结果（多条用换行连接）
- `severity/priority`：致命=主流程阻断/数据丢失；严重=核心功能或数据错误；一般=普通功能问题；轻微=UI/文案。数据不一致类默认「严重」，优先级默认「中」
- `assignee/verifier`：按 `scripts/模块人员映射.csv` 推断（先按 scripts/config.json 的 project_name 过滤项目列，再用 module 关键词模糊匹配）；用户明确指定时以用户为准；匹配不到则留空并在确认环节提示
- `images`：截图本地路径数组

## 场景B：用户反馈 bug（原样提交）

用户/客服反馈的 bug，**描述保持原文，不改写、不优化、不猜测**。

规则：

1. `description` 字段直接放反馈原文（含任务ID、时间、公司名等明细），此时 steps/expected/actual 不必填
2. `title` 只做提炼：去掉 @人名和编号，保留原句主干，不润色
3. 仅剔除明显的占位垃圾行（纯数字「1」「11」、内部备注如「往后需要自己添加」）
4. 批量导入（docx/Excel/Markdown 清单）时：先解析出完整清单给用户确认（条数、标题、负责人、跳过项），确认后再批量创建
5. 图片：docx 用 python-docx 按编号标题分组、表格 a:blip 提取；能带图就带图
6. 负责人按原文 @人名；需求类条目按用户指示处理（如建为缺陷并标【需求类】前缀）

---

## 两个场景共用

- **先确认再创建**：草稿（场景A 输出模板代码块 / 场景B 输出清单）展示给用户，确认后才执行：
  `<工具包根目录>/.venv/Scripts/python.exe scripts/create_bug.py --file <临时文件>`
- 创建成功后返回缺陷ID，提醒用户到云效核对；临时 JSON 文件用完即删
- 简体中文撰写，术语与系统页面文案保持一致
